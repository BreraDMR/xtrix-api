## 📋 Пошаговая инструкция

### Шаг 1: Применить миграцию

**ВНИМАНИЕ:** Перед применением миграции убедитесь, что у вас есть резервная копия базы данных!

```bash
# Перейти в директорию проекта
cd C:\Users\natal\OneDrive\Plocha\medic

# Проверить текущую версию миграции
alembic current

# Применить миграцию
alembic upgrade head

# Проверить что миграция применена
alembic current
```

Должно показать: `0011_add_specialist_types (head)`

### Шаг 2: Протестировать backend

#### Вариант A: Запустить тестовый скрипт
```bash
python scripts/test_specialist_types.py
```

#### Вариант B: Проверить вручную через API

1. Запустить сервер:
```bash
uvicorn app.main:app --reload
```

2. Открыть документацию API:
```
http://localhost:8000/docs
```

3. Протестировать endpoints:
   - `GET /specialist-profiles/types` - получить список типов
   - `POST /users/` - создать пользователя со specialist_type
   - `POST /specialist-profiles/` - создать профиль

### Шаг 3: Реализовать фронтенд

См. подробное описание в `SPECIALIST_TYPES_UI_IMPLEMENTATION.md`

**Приоритетные задачи:**

2. **Создать компонент выбора типа** (`frontend/src/components/SpecialistTypeSelector.tsx`)
   - Компонент с группировкой

3. **Добавить переводы** (`frontend/src/i18n/translations.ts`)

4. **Создать страницу профиля** (`frontend/src/pages/SpecialistProfile.tsx`)
   - Просмотр и редактирование профиля
   - Поля для расширенной информации

5. **Добавить валидацию для healthcare** (`frontend/src/components/ClientForm.tsx`)

## 📝 Важные замечания

1. **Обратная совместимость:**
   - Все существующие пользователи продолжат работать
   - Поле `specialist_type` nullable
   - Старые специалисты могут работать без типа

2. **Данные:**
   - Существующие специалисты не будут иметь `specialist_type` после миграции
   - Можно заполнить вручную через API или админ-панель

3. **Производительность:**
   - Индексы добавлены для оптимизации запросов
   - Фильтрация по типу/категории быстрая
